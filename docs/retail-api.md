# 商业 API：供货隔离、钱包和对账

本功能复用 New API 的用户、渠道和钱包，让站长的订阅供货与第三方中转服务通过同一入口售卖。客户已有托管账号继续使用专属路由。功能默认关闭；代码验证通过不代表已经配置供货、完成真实收款或达到可售容量。

## 首版范围

- 客户在现有 API 密钥页面创建 `service_mode=retail` 的“余额计费 API”Key。已有 Key 不允许修改业务类型，切换服务需要创建新 Key。
- 上游通过已有渠道页配置，只允许 OpenAI 兼容（type 1）和 Anthropic（type 14）。订阅供货先由 vm2api 转为兼容接口；第三方服务直接接入渠道。
- 客户可调用 `POST /v1/chat/completions`、`POST /v1/responses`、`POST /v1/messages`，支持同步响应及 SSE；可用 `GET /v1/models` 查看可售模型。
- WebSocket、Realtime、Playground、异步任务、compact、count_tokens、图片/音视频专用接口不在本期开放范围。此限制按 API 路径执行，并非对兼容文本接口中所有多模态字段做能力认证。
- 使用 Responses 续聊时，客户端可以随 `input` 重发历史消息及 reasoning、compaction 项的 `encrypted_content`。上游决定能否使用该密文。使用 `previous_response_id` 时，本地需能核对原 Key、渠道和上游凭据，上游需能找回前文。遇到 `previous_response_not_found` 时，可改用完整历史重试。
- 账务管理提供 root 会话 API 和渠道页“中转账务”入口，支持三类账本查询与预留释放；尚无自动采购账单导入或实时利润报表。

## 供货配置

环境变量指定一个绝对路径的普通 JSON 文件：

```text
RETAIL_RELAY_CONFIG=/run/new-api/retail.json
```

以下是示例 ID，不能直接照搬到生产：

```json
{
  "enabled": false,
  "group": "retail",
  "supplies": [
    {"channel_id": 101, "kind": "subscription"},
    {"channel_id": 102, "kind": "reseller"}
  ]
}
```

配置限制：文件不超过 64 KiB，不使用符号链接；至多 100 个不重复的正整数渠道 ID；`kind` 只能是 `subscription` 或 `reseller`。开启时必须有供货，组名为 1–64 位字母、数字、下划线或横线，不能为 `auto` 或以 `acct_` 开头。建议文件权限 `0600`，以只读目录挂载。

启用前在渠道页建立站长专用渠道，配置上游地址、Key、模型、映射和优先级，再把渠道加入销售组。销售组还必须存在于分组倍率配置，并为可售模型设置明确售价。不要使用客户托管渠道，哪怕暂时没有流量：带 `acct_` 分组或存在于当前托管绑定表 `account_hosting_bindings` 的渠道会被剔除。

`kind` 仅标记采购归属，不自动登录订阅账号，不验证供应商余额，也不把订阅费换算成逐 token 成本。站长需先分别验证真实 GPT / Claude 账号及第三方接口，才能把它们标为供货。

配置每次选路读取，普通选择、pin、亲和选择及重试共用约束：

- `retail` Key 只能命中有效供货白名单，分组由服务器决定。
- 其他 Key 排除所有已登记商业供货，不能借旧组或历史亲和绕过商业账本。
- `enabled=false` 停止商业调用，但仍隔离 `supplies` 中的渠道。把配置条目删除意味着将该渠道交回旧路由管理，不是单纯停售。
- 未设置环境变量时保留原有业务。显式文件缺失、JSON 损坏或条目非法时，无法安全确定供货边界，会拒绝包括旧 Key 在内的选路。运维应先离线检查 JSON，再在挂载目录中原子替换；不要清空正在读取的文件，也不要通过移除配置解除隔离来处理故障。
- 初期要求 `common.RedisEnabled=false` 且 `common.BatchUpdateEnabled=false`。否则商业 Key 创建及调用关闭；本实现未验收 Redis 缓存和批量余额写回的组合。不要为了开售在其他业务运行期间随意切换全局缓存配置。

托管 Key 的显式模式为 `hosting`，必须拥有合法名额；空模式兼容原版 Key。托管关闭或名额无效时，不允许显式托管 Key 静默转为钱包消费。已有客户账号不会自动变成公共供货。

## 计费与故障处理

以下为尚未发布人民币价表时的兼容行为；发布价表后，使用下一节的冻结报价、预算预留和暂停规则。

`retail_charges` 将钱包与 Key 额度放在同一事务中预留、结算、退款；请求 ID 由服务器生成。该幂等范围是一笔服务器请求，不是客户端重复提交同一提示词的全局去重。

每次上游调用前写入 `retail_attempts`，失败则不发送。每次尝试记录渠道、供货类别、状态和结构化 usage，不保存提示词及响应正文。HTTP 200 的断流会记为 `interrupted`，协议失败或 incomplete 也保留真实状态。

- 明确 429 且没有输出、请求未取消时，最多重试一次；并受原有重试次数和亲和策略约束。5xx、超时、取消或已有输出后不自动重试。
- 客户按本次售价及可核对用量结算一次。缺失或本地估算 usage 时按 0 结算并退还预留，不把估算值当真实上游账单。
- 钱包不足或提交结算失败时不制造负余额，账本保留 `reserved`；消费日志的 `retail_billing_status=pending_review`，不会把计算额当作已结算收入。计算额保存在管理员日志字段中。
- `reserved` 已从可用余额预扣，不能再当作销售收入。进程退出可能留下该状态；没有自动补扣或自动超时退款任务。root 需核实上游结果及是否仍有在途请求，至少 24 小时未更新后才可人工退款。
- 付费模型即使预估为 0，也至少预留 1 个额度单位。预留不是完整输出费用保证；若最终消费超过剩余额度，仍需人工核对。开售前应结合真实模型设置输出上限、并发与速率限制。
- `CostState=unknown` 是未知采购成本，不是 0。供应商账单确认后可登记尝试成本；订阅成本按期间单独登记。币种最小单位不得与钱包 quota 或其他币种直接相加计算利润。

销售统计仍使用原有用户、渠道、消费日志；持久账本是金额核对依据，不能把单独统计日志当作事务凭据。

## 官方单价与上游分组倍率

人民币定价是独立的商业 Key 合约，不改变旧版计费表达式的美元语义。后台「渠道 → 中转定价」分别维护官方基价、产品路由和上游倍率。星行渠道可以在「分组倍率绑定」选择本站用户分组、供货渠道和上游分组；保存后按需开启自动跟价。其他上游仍支持手动导入倍率，两种方式均不能修改官方单价。客户在「API 密钥 → 价格上限」选择产品、接受浮动价格，并填写价格上限、单次及每日预算。模型广场展示当前账号可用产品的人民币售价。

### 计算口径

所有基价以每百万 Token 为单位，明确区分输入、输出、缓存读取、缓存写入及一小时缓存写入。上下文阶梯按整次请求的完整输入上下文（含缓存）选择，不能用普通输入量代替。官方模型别名必须明确映射到真实官方型号，并记录来源链接、核验时间及有效期。

- 官方以 USD 报价：依供应商约定，数值按 1:1 作为 CNY 基价。这不是外汇汇率换算。
- 官方以 CNY 报价：直接使用人民币数值，例如 DeepSeek；不再做一次兑换。
- 采购单价 = 官方基价数值 × 上游分组倍率。
- 销售倍率 = 上游倍率 × (1 + 成本缓冲) ÷ [实收比例 × (1 - 支付手续费率) × (1 - 目标毛利率)]。
- 实收比例表示每发出 1 元额度实际收到多少人民币。赠送、折扣或兑换码会改变它，不能默认所有额度都按原价售出。
- `wallet_cny_per_unit` 明确约定每个历史钱包展示单位抵扣多少人民币，仅用于扣减换算。它不是模型基价汇率，也不会改写旧余额、历史充值和账单。现有钱包/用量图仍沿用钱包单位；人民币实际扣费与价格版本另存于账本及消费日志。

金额用十进制字符串计算，最终价格及费用向上取整，不用二进制浮点计算差价。比如官方输入单价数值 10、上游倍率 0.24、目标毛利 20%、实收比例 1、手续费和缓冲均为 0，输入售价是 ¥3 / 百万 Token；上游变为 0.4 时，新售价是 ¥5 / 百万 Token。这是计算示例，不是任何真实模型的报价。

### 首次配置与日常导入

首次配置需要站长核实官方型号、上下文阶梯和供货渠道绑定，并明确历史钱包单位与人民币的对应关系。`products[].user_groups` 指用户所属分组；`routes[].rate_id` 指手工上游计价分组；已绑定渠道按用户分组使用绑定的公开倍率，`rate_id` 可留空。绑定渠道所服务的每个产品用户分组都必须有对应绑定，否则拒绝发布。上游各分组使用各自凭据/渠道，渠道中的最终模型名必须与 `routes[].models` 一致。

核心字段：

| 配置 | 字段与约束 |
| --- | --- |
| 官方基价 `models[]` | `id` 客户模型名；`official_model` 官方型号；`currency` 只能是 USD/CNY；`source` HTTPS 官方说明链接；`verified_at` / `valid_until` Unix 秒，有效期最多 366 天；`max_output`；按 `up_to` 递增的 `tiers` |
| 阶梯 `tiers[]` | `up_to` 最大输入上下文；`prices` 必须完整包含 `input`、`output`、`cache_read`、`cache_write`、`cache_write_1h` 五个十进制字符串，不适用项经核实后明确填 `"0"` |
| 产品 `products[]` | `id`、`name`、`user_groups`、`routes`；每条 route 包含已登记的 `channel_id`、`rate_id` 和 `{客户模型名: 上游模型名}` 的 `models` 映射 |
| 上游倍率 `rates[]` | `id` 必须对应 route 的 `rate_id`，支持中文；`multiplier` 正十进制字符串；`verified_at` / `valid_until` Unix 秒，有效期最多七天 |

倍率文件是数组，可选择 JSON 文件或粘贴。下面仅演示结构：两个时间的 0 必须替换为实际核验时间和到期时间，倍率也必须核对当前上游账号；原样导入会被拒绝。

```json
[
  {"id":"上游分组名称","multiplier":"0.24","verified_at":0,"valid_until":0}
]
```

导入替换完整倍率快照；正在被产品引用的分组不能静默丢失。点击「发布价表」会自动计算并打开人民币售价预览，确认后才发布；单独的预览按钮仅用于试算。修改任何草稿字段都会使原预览失效。并发发布用 `expected_version` 检查，冲突时刷新后重做预览，不能覆盖其他管理员的更新。

| 接口 | 权限与用途 |
| --- | --- |
| `GET /api/retail/admin/pricing` | root 会话，读取价表与版本 |
| `PUT /api/retail/admin/pricing` | root 会话，`{expected_version, book}` 发布完整价表 |
| `POST /api/retail/admin/pricing/rates` | root 会话，`{expected_version, rates}` 只更新上游倍率 |
| `GET /api/retail/admin/pricing/group-bindings` | root 会话，读取本站用户组、已批准星行供货渠道、绑定及同步状态 |
| `PUT /api/retail/admin/pricing/group-bindings` | root 会话，`{expected_version, bindings, enabled, sale_policy}`；绑定含 `local_group`、`channel_id`、`upstream_group`，倍率由服务端重新读取。`sale_policy` 含 `receipt_ratio`、`margin_bps`、`fee_bps`、`buffer_bps`；旧客户端可省略以保留现值 |
| `POST /api/retail/admin/pricing/group-bindings/sync` | root 会话，`{expected_version}`，立即同步已经开启的绑定 |
| `POST /api/retail/admin/pricing/preview` | root 会话，`{book}` 预览，不发布 |
| `GET /api/retail/catalog` | 用户会话，只返回授权产品的售价，不返回采购倍率及渠道 ID |
| `GET /api/retail/keys/:id/pricing` | 用户本人 Key 的限价与修订号 |
| `PUT /api/retail/keys/:id/pricing` | 用户本人 Key，`{expected_revision, policy}` 保存明确同意和预算 |

`policy` 包含 `product_id`、`accept_floating=true`、按客户模型名索引的 `caps`（五类人民币单价上限）、`max_request_cny`、`daily_budget_cny`。每日预算按 UTC 日历日计算。价格更新不会自动提高用户的上限，也不会替用户勾选同意。

### 请求和结算边界

每个请求在同一数据库事务中确认价表版本、用户产品权限、Key 限价、单次/每日预算、钱包和 Key 额度，再保存不可变报价。预留使用本次请求实际计数的输入 Token 与请求声明的输出上限；兼容缓存计数可能重叠，因此输入侧仍按四类计费项的最高单价乘以实际输入长度预留。预览等没有具体请求的场景继续使用模型最大上下文作为理论边界。真实结算后退回未用部分。

在发送前再次检查实际渠道、映射后的模型、参数覆盖后的输出上限、完整请求和当前价格版本。发布新版本会阻止尚未发出的旧版请求；已经发到上游的请求按冻结售价结算。便宜线路不能重试到更贵线路；本模式不自动重试任何已尝试的上游调用。

- 售价超过用户上限返回 `retail_price_cap_exceeded`；预算不足返回 `retail_budget_exceeded`。均在调用上游前拒绝，不产生该次采购费用。
- 上游倍率或官方基价过期、已发布价表暂停时拒绝新请求。只有从未发布价表的 version 0 保留旧行为；暂停不会回退到旧计费。
- 输出默认上限为 1024（受模型上限约束）；模型映射、数量及输出上限不能在参数覆盖阶段绕过检查。
- 首版仅接受完整上下文的文本请求及普通函数工具。图片、音频、内置计费工具、加速服务档位、状态化上下文、多个候选输出和重复 JSON 字段被拒绝。
- 缺失、估算、非法或超出报价边界的 usage 不会当作真实用量结算，预留进入人工核对。明确失败可退款；未知结果不自动退成免费调用。
- 原 UTC 日的预留会在同一账务事务中结算或人工退款，跨日不会让在途请求的预算消失。重复结算/退款不重复扣钱。

手动导入无法获知供应商未通知的即时涨价。有效期和缓冲只能限制风险窗口，不能承诺绝不亏损；若要进一步收紧，需供应商提供可验证的倍率接口，以及请求锁价或采购费用上限。不得把截图上的历史倍率、渠道别名或本仓库测试夹具当作正式价表。

## 官方支付宝钱包充值

复用已存在的官方支付宝公钥模式，钱包与托管购买使用不同订单表和配置变量：

```text
ALIPAY_WALLET_CONFIG=/run/new-api/alipay-wallet.json
```

```json
{
  "enabled": false,
  "environment": "production",
  "app_id": "REPLACE_WITH_MERCHANT_APP_ID",
  "seller_id": "REPLACE_WITH_SELLER_ID",
  "app_private_key_file": "/run/new-api/alipay-app-private.pem",
  "alipay_public_key_file": "/run/new-api/alipay-public.pem"
}
```

商户 ID 占位符必须替换为真实数字 ID。私钥、配置权限限定为 `0600` / `0400`，不提交到 Git。网关由官方 SDK 固定，不能由浏览器输入；回调和回跳必须使用 HTTPS。应用启动时读取一次支付宝配置，变更后需要按发布流程重启服务。新订单还要求站点已有支付声明确认生效。

充值入口沿用钱包页，提交 `POST /api/user/pay`：

```json
{"amount":1,"payment_method":"alipay_official"}
```

`amount` 沿用站点钱包的展示单位及兑换配置，不是固定人民币分。服务器计算人民币金额并冻结入账 quota；其后修改兑换率不会改变旧订单。

- 通知地址：`POST /api/wallet/alipay/notify`，只接受不超过 64 KiB 的唯一表单字段；拒绝 query 参数、重复字段、错误签名、错误应用/收款人/金额。通知通过 RSA2 验证后才入账。
- 订单归属、交易号唯一约束和数据库事务防止重复入账；通用后台补单不能绕过官方核验。
- 本人补查：`POST /api/user/alipay/query`，JSON `{"order_id":"WP..."}`。只接受有效门户会话并核对订单所有者。
- 后台每分钟有界扫描七日内未决订单，按官方查单结果补偿通知丢失；查单失败保留原状态，前端回跳不发钱。
- 退款等异常通知进入 `paid_review`，不会自动猜测退款金额并扣回客户余额，也不会让后来的支付通知重复入账。需要人工处理，不包含自动退款产品。
- 关闭新订单后，保留原商户配置，以继续核验旧通知/查单。不要在旧订单未处理完时更换商户身份。

本轮未配置真实商户、未发起真实付款；本地签名、回调、防重测试与浏览器模拟页面不能替代真实支付验收。

## root 账务 API

仅允许 root 门户会话；个人访问令牌和普通 API Key 不能调用。写操作还应用同源保护与请求频率限制。使用正常登录的管理会话，不把会话或上游凭据写进脚本示例。

| 接口 | 用途 |
| --- | --- |
| `GET /api/retail/admin/accounting` | 每次至多返回各 100 条 charges、attempts、costs |
| `POST /api/retail/admin/charges/:id/refund` | 人工释放超过 24 小时未更新的预留 |
| `POST /api/retail/admin/costs` | 追加真实采购成本 |

账务查询可用 `request_id` 精确过滤。翻页使用回包 `data.next`：charges 的 `charge_before` 与 `charge_id` 必须一起传；attempts、costs 分别使用 `attempt_before`、`cost_before`。它们是三个独立序列，没有 next 的序列已到尾；不应不断重读它。同秒多笔账单不会仅因时间游标被跳过。按请求过滤时成本只含该请求尝试，订阅期间成本需另查。

退款示例（`expected_reserved` 是读取到的 quota 整数）：

```json
{"expected_reserved":100,"reason":"已核实没有在途请求，供应商未产生费用"}
```

金额必须与账本一致；重复相同审核不重复退款。已结算消费的商业退款不由此接口处理。

逐次成本示例（USD 分，非钱包 quota）：

```json
{"reference":"supplier-invoice-line-001","kind":"attempt","attempt_id":12,"channel_id":102,"currency":"USD","amount_minor":3}
```

订阅成本示例（仅适用于登记为 subscription 的供货）：

```json
{"reference":"subscription-invoice-2026-11","kind":"subscription","channel_id":101,"currency":"USD","amount_minor":2000,"period":"2026-11"}
```

示例金额只是字段演示，不是采购价格建议。`reference` 唯一，重复同一内容可重试，重复凭据但内容不同会拒绝；操作者及时间由服务端填充。首版只追加已核实记录，没有更正/撤销成本接口，不能随意登记估算值。

### 2026-11-16 模型工作台

### 本站分组绑定与自动跟价

进入「渠道 → 中转定价 → 分组倍率绑定」，读取上游分组后添加一行，依次选择本站用户分组、供货渠道、星行分组。这里的本站组对应用户所属组和产品的 `user_groups`，不会改写旧版 `GroupRatio`。一个渠道对应一个上游 Key；同渠道可以服务多个本站组，但只能绑定同一个星行组。绑定不能替上游 Key 切组，管理员必须确认 Key 的真实分组；公开接口不能核验专属折扣。

目标毛利率直接在跟价区设置，点击「保存绑定与毛利」与绑定、跟价开关一起原子保存。自动同步只更新采购倍率，保留经营参数。毛利率及高级选项中的实收比例、手续费、缓冲适用于全部零售产品；不是单条绑定的独立利润配置。每行显示的预计售价倍率只作展示，正式报价仍由服务器十进制计算。无手续费、折扣和缓冲时，上游 0.12、毛利 20% 对应售价倍率 0.15；上游涨到 0.16 后对应 0.20。

星行自动跟价无需上传倍率文件。手工倍率导入折叠在「手工倍率 · 其他上游」，只用于没有自动跟价的供应商。保存经营参数不要求先上传官方价表，也不会开启销售；真正开放调用前仍需配置已核实的官方价表、产品路由和钱包单位。已有绑定时，普通价表预览和发布保留单独保存的经营参数；下方有未保存草稿时，保存跟价会保留草稿并要求刷新后再预览发布，避免旧草稿覆盖新毛利。

模型工作台会分别提示站点暂停、账号分组未分配产品、当前没有可报价模型、未设置用户预算或当前模式未授权模型。站点配置未就绪时不再只提示设置预算，避免用户反复保存预算仍无法选择模型。root 可通过「配置模型与定价」进入渠道页继续配置；普通用户只看到联系管理员的提示。页面不自动开启销售、分配权限或创建付费身份，服务端仍独立检查预算和模型权限。

渠道候选来自私有供货白名单，只允许 `reseller` 类型且地址为 `https://aixingxing.pro` 的供货渠道；托管客户渠道不能参与。可先保存对应关系，官方型号、产品路线和经营参数仍需单独配置并发布。保存绑定不会开启「接收新计价请求」；首次保存后也不会回退到未发布版本的旧计价。已被产品使用的绑定不能直接删除，先移除产品路线，或关闭跟价暂停该绑定路线。

开启后，服务器通过数据库任务租约每分钟读取一次固定公开接口，多个进程共享版本。读取失败或绑定组缺失时，绑定路线暂停报价，不使用零倍率或旧手工倍率。界面的重新载入按钮可读取后台最新状态；有未保存选择时不要刷新。已经发往上游的请求保留原报价，新请求仍受目标毛利、手续费、成本缓冲、密钥限价及预算约束。

倍率变动和绑定编辑生成新版本；只有时间更新且价格不变时续期，不每分钟复制整份审计价表。并发保存拒绝覆盖，普通价表发布和手动导入无法改写绑定或公开同步数据。最终发送还校验采购地址，渠道改到另一供应商时拒绝套用星行成本。

每分钟轮询存在变化发现窗口，不能保证上游瞬间抬价时绝不亏损；需要更严格保证时，应向上游申请请求锁价或费用上限。

工作台用户可直接选择有权限的调用分组和模型；新身份使用默认消费保护，普通 API Key 选择调用分组即可。系统按允许的上下文与输出上限预留，自动跟价模式会在单次预算内限制输入长度，不擅自降低输出上限；结算按实际用量扣费并释放多余预留。上游模型目录可读不代表生成成功；上游余额不足时仍需先充值上游账号，本站余额与上游余额分别管理。


### 公开调用分组（2026-11-17）

调用分组是用户选择的供货线路，如 `gpt-normal`、`gpt-plus`，与账号所属的 `default` 等权限组分开。
在供货绑定中设置分组后，点击「生成官方价表与调用线路」，预览并发布；自动生成的调用分组向所有注册用户开放。工作台与 API Key 使用同一调用分组目录。工作台可直接发送，普通 API Key 选择调用分组即可。

产品字段 `public: true` 表示向所有已认证用户开放，`binding_group` 固定其采购倍率绑定。公开访问不改变登录、Key 归属、渠道供货资格和预算检查。每条线路仍按官方基价、绑定的上游倍率与站点毛利生成售价；失败或过期的倍率不会按账号组回退。

已有价表读取时不自动扩大权限。明确执行生成操作只升级原有 `official-*` 生成器创建且保持原始单组权限的产品，发布后才生效。手工私有产品继续使用 `user_groups`，历史无 `binding_group` 的私有产品保持旧行为。

工作台切换分组会清空已选模型与当前会话。自动跟价模式按每次请求携带的分组报价，不修改共享预算；手工模型限价仍限定在原来保存的分组，跨组需在消费保护中显式修改。公开分组可见不代表上游余额或模型调用已验证。


### 工作台直接发送与发布确认

- 新工作台身份默认按当前售价使用，单次最多 ¥5、每日最多 ¥50（UTC 日界）；钱包不足、预算不足、私有分组无权限、倍率过期或价表暂停均会在采购前拒绝。页面显示消费保护入口和金额，不要求首次确认或逐模型填价。
- 管理员可在服务器的 `RETAIL_RELAY_CONFIG` JSON 设置 `studio_max_request_cny` 和 `studio_daily_budget_cny`（正数字符串）。未设置时使用 `"5"`、`"50"`；仅初始化没有保存策略的身份，不重置已保存限制。
- 「消费保护」可调整金额，也可关闭「在预算内按当前价格使用」后展开「高级设置 · 模型单价上限」。已有手工上限保持原样，不能通过切换调用分组、刷新页面或重复首次发送绕过。
- Enter 发送，Shift+Enter 换行；中文输入法选字和长按重复按键不会触发发送。聊天和生图共用同一个持久身份及每日预算，调用分组只属于当次请求，避免多标签页相互改组。
- 长上下文的最高预留超过单次预算时，自动模式缩小允许的输入长度，并在初始请求、最终上游请求和实际用量结算处校验；输出额度本身超预算时直接拒绝。预留仍为保守上限，结算后退回未用金额。
- 「发布价表」自动试算并展示所有价格档位，确认时发布被审阅的那份草稿；取消不写入，试算期间改草稿会使确认失效，并发发布仍检查价格版本。
- 已发布有效价表的线路不再依赖旧 `GroupRatio` 中是否保留内部 `retail` 名称。公开/私有产品授权、供货白名单、价表版本和消费保护继续独立校验。

以上描述为本地实现；生产是否启用应以实际发布提交和现场请求验收为准。回归使用合成上游，不代表真实供应商模型生成成功。

### 创建 API Key 时选择调用分组

中转站创建 Key 时填写名称、选择调用分组即可保存，不再要求模型单价上限、单次预算、每日预算或跟价确认。已有 Key 点击列表中的分组即可切换；费用按分组当前售价从余额扣除，后台毛利与上游倍率同步规则继续生效。

`POST /api/token/` 使用 `retail_product_id`，服务端在同一事务内创建 Key 和 `group_current: true` 策略。`PUT /api/retail/keys/:id/pricing` 使用 `expected_revision` 与 `product_id` 切换分组。保存后不存储虚构的限额或用户同意；旧的显式策略会在用户保存分组时被替换。旧 API 客户端仍可提交显式 `retail_policy`，但不能与新分组字段混用。

公开分组可供注册用户选择；私有产品权限、Key 归属、同源写入、版本冲突、钱包余额、既有 Key 额度及供应商有效期仍由服务端检查。切换调用分组不改变账号所属权限组，不修改工作台已有预算。钱包按已验证的输入与输出边界预留，结算后退回未用部分。

验证包含创建和切组、旧策略替换、权限与并发冲突、错误回滚、当前价格扣费和余额不足拒绝；数据库使用真实 SQLite、MySQL、PostgreSQL。认证边界沿用 OWASP Authentication、Session Management、Authorization 与 CSRF Cheat Sheets 的要求；不代表全站 ASVS 合规认证。

### 分组上架与自动定价

管理后台的分组页可以直接保存并上架，人民币售价预览可选。服务器在一次事务里检查当前价表版本、指定上游分组的倍率和各条线路的可售模型。缺价模型会显示在跳过清单里。如果没有可售模型，或某条所选线路一个模型都不能供货，本次上架不生效。

零售站开放销售后每六小时读取 OpenAI 和 Anthropic 官方标准价。系统只更新已有的、型号和计费维度能准确匹配的美元价格。旧价首次与官网吻合后进入跟随；不同的历史定价继续保留。管理员手动修改已保存的价格会将该模型标为 `price_mode: manual`，也可以在导入时显式设置。自动任务记录核对结果，金额变化生成新版本。读不到或无法识别的价格不会续期，已核实的价格在有效期内继续使用，过期后暂停新报价。GPT-5.6 Sol 保留已核实的促销截止时间。已经受理的请求沿用受理时的价格。

渠道的「自动定价」页显示正在跟随官网的模型数量和例外。本站分组仍按绑定的上游分组读取倍率，并沿用本站毛利、手续费等设置。全站手工价表导入和停售开关保留在「手动维护价表」。
